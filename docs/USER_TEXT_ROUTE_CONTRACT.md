# قرارداد رسمی مسیر متنی (`user_text Route Contract`)

**هدف:** استانداردسازی ساختار داده‌ای مسیر بارنامه در بستر BarPro، حذف هرگونه وابستگی به GPS/مختصات، و تعریف دقیق قوانین رفتار سامانه در مواجهه با داده‌های مسیر.

---

## ۱. ساختار استاندارد Payload

```json
{
  "route_source": "user_text",
  "location_mode": "user_text",
  "origin": {
    "province": "تهران",
    "city": "تهران",
    "district": "منطقه ۱",
    "address": "خیابان آزادی، پلاک ۱۰",
    "coordinates": null
  },
  "destination": {
    "province": "البرز",
    "city": "کرج",
    "district": null,
    "address": "بلوار جمهوری، کوچه لاله",
    "coordinates": null
  }
}
```

---

## ۲. قواعد و الزامات غیرقابل تخطی

1. **حالت پیش‌فرض (`location_mode="user_text"`):**
   در تمام درخواست‌های ایجاد بارنامه، مقدار `location_mode` و `route_source` برابر با `user_text` است.

2. **بی‌اعتباری و نادیده گرفتن مختصات:**
   در صورتی که در Payload ورودی شیء `coordinates` وجود داشته باشد، مقادیر آن نادیده گرفته شده و در شیء خروجی پردازشگر برابر `null` تنظیم می‌شود. وجود، نبود یا اشتباه بودن مختصات جغرافیایی به هیچ عنوان نباید منجر به شکست فرآیند مسیر یا تغییر نام استان/شهر/آدرس گردد.

3. **منع اصلاح با ژئوکدر یا حدس (No Guessing / No Reverse-Geocode):**
   در صورت ناقص بودن هر یک از ۳ فیلد اصلی (`province`, `city`, `address`) در مبدأ یا مقصد، سیستم به هیچ عنوان مجاز به فراخوانی سرویس‌های ژئوکدینگ (مانند Nominatim/OSM یا map.ir) جهت پر کردن یا حدس زدن فیلدها نیست.
   در این شرایط، Job بلافاصله به وضعیت `NEEDS_REVIEW` منتقل شده و خطای `location_data_incomplete` ثبت می‌شود.

4. **فرمول کلید یکتای مسیر (Canonical Route Key):**
   شناسه و کلید یکتای مسیر منحصراً از ترکیب مقادیر متنی کاربر به فرمت زیر مشتق می‌شود:
   $$\text{Route Key} = \text{SHA256}(\text{Origin: } [P|C|D|A] \to \text{Dest: } [P|C|D|A])$$
   مختصات جغرافیایی (Lat/Lng) هیچ نقشی در تعیین هویت مسیر ندارند.

5. **تفکیک آدرس‌های متفاوت:**
   دو مسیر با استان و شهر یکسان اما با متن آدرس متمایز، باید دارای Route Key کاملاً متفاوت باشند.
