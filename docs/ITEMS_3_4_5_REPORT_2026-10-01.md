## مورد ۴ — Tenant Isolation (تکمیل شد ✅)

منبع: `~/workspace/tenant-isolation-audit/report-2026-10-01.md` (خوانده و مستقل تأیید شد)

### GAP-1 — `GET /api/v1/otp/latest` (HIGH)
- **مشکل:** کلید سراسری Redis `rpa:otp:latest` شامل کدهای OTP زنده همه tenantها بود و هر tenant احرازهویت‌شده می‌توانست بخواند
- **رفع:** حالا `get_current_admin` — فقط master admin (`app/api/routes/otp_forwarder.py`)

### GAP-2 — `POST /api/v1/otp/submit-manual` (HIGH)
- **مشکل:** `job_id` دلخواه بدون بررسی مالکیت پذیرفته می‌شد؛ worker کلید `rpa:otp:job:{job_id}` را اول چک می‌کند → امکان خراب‌کردن submission tenant دیگر با OTP جعلی
- **رفع:** برای clientها `job_id` اجباری شد؛ کوئری `(WaybillJob.client_id == client.id) AND (job_id)`؛ job خارجی/ناموجود → 404، بدون job_id → 403. مسیر سراسری فقط برای admin

### GAP-3 — `GET /waybill/tasks/{task_id}` (MEDIUM-HIGH)
- **مشکل:** فقط `require_sensitive_auth` (بدون هویت tenant) + کوئری بدون فیلتر client → هر credential معتبر (حتی API key مشترک) می‌توانست job هر tenant را بخواند
- **رفع:** تغییر به `get_current_user_or_admin`؛ `task_service.get_task_status(task_id, client_id)` کوئری را اسکوپ می‌کند؛ legacy IDهای غیر `job_*` برای client → ۴۰۴ (`app/api/routes/waybill_map.py`، `app/services/task_service.py`)

### تست‌های رگرسیون جدید
`tests/test_tenant_isolation_gaps.py` — ۱۰ تست، همه سبز:
- tenant محروم / admin مجاز برای OTP سراسری
- کنترل منفی job خارجی، کنترل مثبت job مالک
- رد client بدون job، موفقیت admin سراسری
- کنترل‌های خارجی/مالک/admin برای وضعیت task
- رد client برای legacy task ID

### تست‌های موجود به‌روزرسانی شدند
